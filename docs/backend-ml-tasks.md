# Бэкенд и прогнозирование Coyote Supply

Готовый сценарий для защиты: две тестовые точки, воспроизводимый расчёт на фиксированную дату, объяснение дефицита и рекомендации, правка заказа и восстановление из SQLite после перезапуска. Global Coffee задаёт рабочий процесс управляющего и ассортимент, Coyote Manager задаёт ожидаемые источники продаж, техкарт и складских данных. Для пилота согласуем поля выгрузки и проверим, какие закупочные функции уже есть у Coyote. Публичные материалы описывают склад, техкарты, выгрузку отчётов и уведомления об остатках. [Global Coffee](https://globalcoffee.info/) · [Coyote](https://coyote-pos.kz/)

Порядок работы: **B01 → B02 → M01 → B03 → B04 → F05 + B05**. После B02 можно начать M02 параллельно с API. B03 и B04 идут отдельными PR после фиксации общего контракта. До готовности B04 фронтенд живёт на фикстурах. [Контракт](api-contract.md) · [Схема](api-schema.json) · [Контрольные ответы](fixtures/)

## B01 · Каркас сервиса и договорённость об источнике

**Владелец:** Spatd. **Выход:** сервис FastAPI запускается одной командой, есть `GET /api/health`, список точек и инструкции запуска.

- Разделить маршруты, модели ответа Pydantic, адаптер входов, чистый расчёт и хранилище. Хендлеры преобразуют ошибки в HTTP, алгоритм получает обычные структуры и запускается отдельно от FastAPI.
- Утвердить единицы `ml/g/pcs`, целые количества и ₸, локальную дату кофейни и timestamp со смещением. Проверять типы, ключи, допустимые диапазоны и обязательные поля на входе. Документировать соответствие выгрузок Coyote внутренним ключам отдельно от контрактных ответов.
- Начать с локального адаптера. Входной формат поставщика данных уточнить у Coyote после демонстрации. Для пилота согласовать обезличенный экспорт, права на точку и частоту обновления снимков.
- Зафиксировать зависимости и команды запуска и тестов. Путь SQLite задаётся окружением. Демо запускается без токенов и внешних сервисов.

**Приёмка:** запуск из чистого клона, health отвечает 200, список возвращает обе точки, неизвестный ID даёт `404 store_not_found`, тесты сверяют форму ответа со схемой. [FastAPI testing](https://fastapi.tiangolo.com/tutorial/testing/)

## B02 · Синтетические исходники и расход по техкартам

**Владелец:** Spatd. **Выход:** версионированный набор с фиксированным seed, генератором и контрольными сценариями.

| Набор | Минимальные поля и проверки |
|---|---|
| Точки и настройки | ID, зона, календарь дедлайнов и поставок, порог свежести снимка. Календарь одной точки независим от другой. |
| Продажи | ID позиции чека, точка, время, SKU и размер, количество, статус или корректировка. Повторный импорт не удваивает расход. Учитываем завершённые продажи по согласованной политике возвратов. |
| Техкарты | SKU и модификаторы, версия и интервал действия, ингредиент, базовое количество. Для каждого чека выбираем версию на дату продажи. Перекрытия версий и неизвестные единицы отклоняем. |
| История наблюдений | Дата, точка, полнота выгрузки, известные остановки продаж из-за дефицита. День с полной выгрузкой без продаж даёт ноль. День без выгрузки остаётся пропуском. |
| Склад, партии и приходы | Время снимка, ингредиент, количество, партии со сроками, подтверждённые приходы с датой и сроком. Время, единицы и суммы партий проверяем при загрузке. |
| Закупочные параметры | Размер упаковки, цена упаковки, резерв и максимум. Проверяем положительный размер, неотрицательную цену и согласованный максимум. |

Посуточный расход равен сумме `проданные единицы × расход по техкарте` по точке и ингредиенту. Для демо нужны 8–12 недель, разный спрос по дням недели и минимум пять различимых ситуаций: ранний дефицит молока, списание сливок, излишек стаканов, неизвестный остаток овсяного молока, другая закупка в Алматы. Даты и цены синтетические. Контрольные ответы API служат ожидаемыми результатами проверки независимо от исходников.

**Приёмка:** одна исходная продажа вручную сходится с техкартой, смена размера или рецептуры изменяет расход, дубликат чека не меняет агрегат, ноль и пропуск различаются, изменение Алматы не меняет Шымкент.

## M01 · Базовый прогноз, который работает в MVP

**Владелец:** Spatd. **Выход:** чистая функция `forecast_demand(history, as_of, dates)` и тесты, которые можно запустить без БД.

1. Строим прогноз расхода ингредиента по точке и дню. Берём до четырёх последних пригодных наблюдений того же дня недели, известных на момент расчёта. Минимум три. Медиану округляем вверх до целой базовой единицы.
2. Пропуски выгрузки и известные дни ограничения продаж исключаем из обучения. У подтверждённого дня без спроса значение ноль. Отмечаем неполное покрытие техкарт, чтобы неизвестный расход не превращался в нулевой спрос.
3. Возвращаем прогноз на дни до следующего прихода после целевого. Записываем версию модели, дату среза и число пригодных наблюдений в диагностику. Недостаточная история переводит затронутую позицию в ручную проверку. Остальные ингредиенты продолжают рассчитываться.
4. Сохраняем отдельные тесты на границу даты, праздник или выброс, нулевые продажи, неполную историю и смешение точек. Внешние погодные данные и промо считаем отдельным расширением после появления надёжной истории.

**Приёмка:** фиксированный вход даёт идентичный прогноз в повторных запусках. Добавление данных после даты среза не меняет уже рассчитанный прогноз. Контрольный результат согласован с [правилами кейса](spec.md).

## B03 · Поставка, партии и объяснимая рекомендация

**Владелец:** Spatd. **Выход:** `GET /api/stores/{id}/forecast` строит прогноз из входов B02 и результатов M01.

- Выбрать первый приход, дедлайн которого ещё доступен на момент расчёта, и следующий за ним. Применять календарь и время точки. Если расписания нет, показать причину ручной проверки.
- Для каждого дня добавить подтверждённые приходы, списать спрос начиная с партий с ближайшим сроком годности, зафиксировать непокрытый спрос, затем отметить остаток партий на дату истечения. Срок включает текущий день. Просроченные к началу среза партии недоступны. При неизвестных сроках явно помечать неполный расчёт списаний.
- Посчитать дефицит до целевого прихода отдельно от потребности окна после него. Поставка 12 ноября не закрывает потерянный спрос 10 ноября. Поздний подтверждённый приход внутри окна учитывается только с его дня.
- Зафиксировать посуточный прогноз для сценария без новой закупки. Для заказа сложить непокрытый расход окна и недостающий резерв, затем округлить вверх до целой упаковки. Излишек сравнить с максимумом в конце окна. Для пилота отдельно проверить срок годности закупаемых партий и стоимость излишка. Изменение политики закупок требует сверки контракта и контрольных ответов.
- Сформировать стабильный `forecastId` из точки, версии снимка, даты расчёта, версии модели и версии правил. Для одного и того же снимка и настроек ID воспроизводим. Обновление данных должно делать прежний ID устаревшим.

**Приёмка:** Шымкент, молоко. Остаток 20 л, потребность до прихода 37 л, первая нехватка 5 л 10 ноября, суммарно 17 л до поставки. На 12–14 ноября расчёт даёт 19 л непокрытого расхода + 5 л резерва = 24 л, 4 упаковки за 16 800 ₸. Сливки дают риск списания 9 л, стаканы — излишек 20 шт. и закупку 0 шт., овсяное молоко — неизвестный остаток и `null` в рекомендации. Дополнительные тесты проверяют две партии с разными сроками, приход после дня дефицита, просроченную партию, день истечения и округление.

## B04 · Хранение и валидация черновика

**Владелец:** Spatd. **Выход:** `GET` и `PUT /api/stores/{id}/draft` по контракту.

- Хранить черновик и его строки по ID точки в SQLite. Цена, число упаковок, суммы, `forecastId` и `savedAt` фиксируются на момент сохранения.
- Перед записью проверить существование точки, актуальность прогноза, уникальность строк, принадлежность ингредиента точке, пригодность к заказу и кратность упаковке. Положительное количество и итог должны помещаться в диапазон целых контракта. Цена берётся на сервере. Позицию с рассчитанным нулём можно добавить вручную.
- Заменить весь черновик атомарно одной транзакцией. Пустой список удаляет черновик. При одновременных запросах действует последняя успешная запись. Если данные обновляются одновременно с записью, проверка версии и запись должны работать относительно одного снимка.
- `409 stale_forecast` сообщает о смене прогноза. `422 invalid_draft` указывает путь строки и причину. Проверить отказ до транзакции и откат при сбое внутри неё. При чтении старый черновик возвращается со своим `forecastId`, чтобы UI мог показать необходимость сверки.

**Приёмка:** сохраняем 30 л и получаем от сервера 5 упаковок и 21 000 ₸. Перезапускаем API с той же БД, `GET` возвращает прежние строки. Некратное количество, чужая позиция, дубль и устаревший ID отклоняются без изменения существующего черновика. Очистка повторяема. Алматы имеет свой черновик. [SQLite transactions](https://www.sqlite.org/lang_transaction.html)

## M02 · Сравнение модели с базовым прогнозом

**Владелец:** Spatd. **Когда:** после B02 и M01. **Выход:** воспроизводимый отчёт, таблица ошибок и решение о включении кандидата.

- Начать с двух сравнений: прошлое значение того же дня недели и рабочая медиана. Если наблюдений достаточно, добавить одну модель `HistGradientBoostingRegressor` с днями недели, лагами 7/14/21/28 и агрегатами только по завершённым дням. Обучать по временным срезам. Подгонка признаков и параметров видит только обучающий отрезок.
- Запустить проверку скользящим окном. На каждом срезе прогнозировать фактический горизонт закупки из данных, доступных на тот момент. Не подставлять фактический вчерашний расход внутрь горизонта. Для первых экспериментов признаки строятся от даты заказа, целевая переменная задаётся по дню горизонта.
- Сравнивать MAE в единицах ингредиента, WAPE внутри сопоставимых рядов и долю дней, для которых доступен прогноз. Если суммарный фактический расход равен нулю, WAPE не определён. Публиковать размер выборки и разрезы по точкам, ингредиентам и горизонту. На одном и том же тестовом наборе сравнить остаточный дефицит и риск списаний после симуляции закупки.
- Включать кандидата только при измеримом улучшении на нескольких временных срезах и без существенного ухудшения по скоропортящимся позициям. Порог улучшения согласовать до просмотра результатов. При слабых данных или сбое кандидата использовать M01 и фиксировать причину. Качество на синтетике проверяет методику. Эффект на реальной точке требует отдельного пилота.

**Приёмка:** одна команда воспроизводит отчёт из зафиксированного набора и версий. В отчёте указаны интервалы обучения и проверки, выбранный метод и причины выбора. [Пример scikit-learn для временных рядов](https://scikit-learn.org/stable/auto_examples/applications/plot_time_series_lagged_features.html)

## F05 и B05 · Сквозная проверка и передача

**Владельцы:** frontend подключает маршруты и состояния UI, Spatd проверяет сервис и SQLite, приёмку проводим вместе.

1. Открыть сборку из чистого клона, загрузить две точки через API. Прогноз и черновик сверять по ID точки. Поздний ответ по прежней точке не должен перерисовывать новую.
2. Пройти Шымкент → молоко → 4 упаковки → 5 → сохранение. Сверить сумму из ответа API. Обновить страницу, перезапустить сервис и повторить `GET`.
3. Проверить загрузку, ошибку сети с повтором, пустой черновик, `422` рядом с полем и `409` с обновлением прогноза и сохранением пользовательского ввода для сверки. Убедиться, что Алматы открывает независимые данные.
4. Подготовить один локальный сценарий защиты и резервный запуск на фикстурах. Подписать источник на экране. Показать пользу на контрольном примере, затем сформулировать, какие выгрузки и критерии качества нужны для пилота.

Работа принята, когда каждый кейс из [спецификации](spec.md) воспроизводится из чистого клона, а расчёт и сохранение подтверждены тестами API и проверкой в браузере.
